# Own-site tennis checkout: local server contract

This implementation prepares a payment experience on maximus.tennis for an authenticated owner of an immutable, approved goods order. It is a reviewed dependency-injection boundary, not a connected production payment integration. The deployed/default `resolveTennisCheckoutRuntime()` returns `service:null` before reading credentials, stores, evidence or provider transports. Portal flags alone cannot activate it. No real session, charge, merchant setting, key, cron or payment callback was created by this work.

## Customer HTTP boundary

`POST /api/accounts/orders/{MX-ORD}/checkout` requires the existing verified portal session cookie, same-origin request and `X-CSRF-Token`. The customer already has a durable unique order-owner link; no bearer order capability is manually supplied to this endpoint. An `Authorization` header, query parameters, caller customer/provider IDs, monetary fields and payment-program fields are rejected. The UTF-8 JSON body is limited to 1,024 bytes and a five-second read deadline, with exactly:

```json
{"idempotencyKey":"opaque-stable-key-8-to-128-characters","termsVersion":"existing-immutable-offer-terms-version"}
```

The authenticated POST constitutes acceptance of that existing immutable terms version. The server records its timestamp before invoking an injected provider creator. It cannot approve a quotation, invent a price or modify the order snapshot. The accepted version must exactly match the approved offer and quotation. An initial order must still be payable and its offer unexpired; later resolution never creates a replacement session after expiry.

The safe response contains only `code`, a request `correlationId`, `status`, `checkoutPath`, `checkoutHandle`, `expiresAt` and `embedded`. Errors also have `messageKey` and `retryable`; they contain no raw adapter/store error. Status is `creating`, `uncertain`, `review_required`, `expired` or `ready`. Unresolved states have `embedded:null`. `checkoutPath` is exactly `/{immutable-order-locale}/checkout` for an existing site locale. The UI may remain on its current locale; the path is not an external redirect. The random handle is `tco_` followed by 43 base64url characters.

Only a currently unexpired, independently verified `ready` receipt can expose:

```json
{"contract":"mpgs_hosted_checkout_embedded_v1","serverVerified":true,"sessionId":"SESSION…","gatewayOrigin":"https://ap-gateway.mastercard.com","sdkVersion":"100"}
```

This descriptor is an audited server-adapter projection, not a claim that arbitrary raw MPGS JSON contains the surrounding fields. Merchant ID, provider order ID, internal correlation, customer identity, amount, provider references and raw proof are omitted. The descriptor is a browser payment capability: responses are private/no-store/no-referrer and the UI must hold it only in memory, never in URLs, analytics, logs or persistent browser storage. The opaque checkout handle is not accepted as authorization by any public session-read route; none is introduced here.

## Durable server service

`createTennisCheckoutService({store,commerceStore,route,createAuthenticatedSession,resolveAuthenticatedSession,now,providerTimeoutMs,production})` exposes `{readiness,checkout}`. `checkout({ctx,orderId,idempotencyKey,termsVersion,signal})` accepts only the trusted portal context supplied by the HTTP authentication boundary. It rereads the active user, tenant membership, durable `portalOrder`, `portal_order_owner` unique and full original commercial order. It uses the unchanged shared `approvedGoodsContract` validator for exact AED total, approved seller, final configuration/technical specification, verified fulfillment, accepted terms and non-TEST quotation with no TEST invoice. It requires no CS-Cart native order for this direct MPGS strategy. Email matching and customer-asserted payment facts cannot create ownership.

The production constructor defaults to `NODE_ENV==='production'` and requires both store interfaces to be identified as `upstash`; anonymous/memory clients are denied. The existing commerce client has no kind tag, so any future reviewed server factory must attach that tag only to its successfully resolved durable commerce client, not to a memory fallback. Default factory remains null. A real Redis test exercises both actual platform atomic commit and commerce Lua CAS interfaces, rather than replacing commerce CAS with a map.

One atomic platform reservation persists a server-generated private correlation, bounded provider order ID, immutable contract hashes, a one-attempt claim, order uniqueness, scoped idempotency and audit. It shares the existing `native_checkout_commerce_order` fence with the separate native association workflow, so the same MX order cannot receive competing direct and native checkout intents. No provider call follows an unacknowledged reservation. A 30-second creating lease prevents competing callers from creating. Replays, process reconstruction, lost provider responses and lost persistence acknowledgements query the original attempt only; they never recreate it. Terminal review/ready/expired states cannot be revived by stale recovery. Ready receipt integrity and effective expiry are rechecked. Every ready response rereads route evidence, current active ownership, immutable contract and the exact commercial pending fence, including concurrent winners and ACK-loss readback.

The commercial document is claimed by actual compare-and-swap from `ready` to `creating`, with accepted terms and the exact private intent fence. A verified session moves the commercial status only to `pending`. No new LIVE session is placed in legacy `payment.session`: that field belongs to the older TEST hosted-page/capability path. Session receipt fields remain private in the platform intent. These are two independently durable stores, not a distributed atomic transaction; a failed cross-store write remains uncertain and recovery checks the original fence. A changed/paid/refunded order does not expose a session.

Provider calls are bounded to six seconds (or a lower injected test timeout) and receive an AbortSignal. The creator receives the exact immutable server intent plus the full claimed commercial document; only an accepted opaque provider reference is retained. A thrown, timed-out or ambiguous result becomes uncertain. The independently authenticated resolver must confirm the exact private correlation/provider order, merchant, selected API version, route, LIVE mode, session contract, snapshot, AED amount, accepted terms, session ID and canonical verification/expiry times. Its authentication basis is `provider_server_session_query`; browser completion or return values do not satisfy it. Verification must be at or after the single attempt. The effective expiry is the earlier of the verified provider expiry and approved offer expiry. No browser response marks an order paid, posts a ledger journal, issues an invoice or sends mail.

## Route evidence and current limits

`normalizeTennisCheckoutRoute` defines a supported future private route contract: project `tennis`, organization `maximus-tennis`, MPGS merchant `300281`, AED, seller MAXIMUS SPORTS EQUIPMENT TRADING LLC, gateway `https://ap-gateway.mastercard.com`, public origin `https://maximus.tennis`, embedded presentation, selected SDK contract `100`, and an explicitly selected positive API version. SDK/API selections in synthetic tests are not the current installed add-on version or proof of merchant support. Current real API version, checkout session schema, authentication method/rights, LIVE route and feature availability are not established by this module.

The stored route hash/version and all five stored evidence rows must match and remain verified on each request: `merchant_hosted_checkout_feature`, `approved_tennis_origin`, `mpgs_checkout_session_schema`, `mpgs_embedded_sdk_contract` and `mpgs_3ds_return_behavior`. Only prior authenticated operator inspection/query/document verification records are accepted. They are not created from customer input, environment flags or a successful local test. No real records are seeded. Actual provider creator/resolver adapters are absent.

The official indexed [Hosted Checkout SDK 100 overview](https://test-gateway.mastercard.com/api/documentation/apiDocumentation/checkout/version/100/api.html?locale=en_US) distinguishes `showEmbeddedPage()` (hosted payment form inside the merchant site) from `showPaymentPage()` (gateway-hosted page). The [AP Hosted Checkout SDK overview](https://ap-gateway.mastercard.com/api/documentation/apiDocumentation/checkout/version/100/api.html?locale=en_US) is the relevant regional source. Its full function documentation was not successfully read in this task. Exact supported `showEmbeddedPage` arguments, current merchant feature/origin permission, session initiation/return contract, browser/3DS behavior and compatibility still require positive primary-source and current-merchant verification before enabling a renderer. The current descriptor does not by itself license loading a guessed SDK integration. No deprecated lightbox is implemented. Hosted Session card fields are a different integration, not silently substituted here.

Current repository defaults have empty approved offers and a formal quotation producer that creates TEST quotations. Existing awaiting-quote/TEST snapshots cannot be promoted by editing their immutable offer/customer/quotation fields. A separately reviewed producer of an authoritative approved non-TEST commercial revision is still needed before real own-site payment. This work does not alter pricing, terms, quotation producers or those reviewed old snapshots. Also missing are a real authenticated direct MPGS session adapter, positively verified embedded SDK/merchant/origin/3DS evidence, independently verified capture callbacks/query adapter for this direct route and its exact owner-to-ledger mapping. The separate CS-Cart native polling bridge is not automatically that direct-route callback adapter. Accounts do not gain balances from creating or returning from this checkout.

The real Redis test owns only `127.0.0.1:6399`, starts the existing binary in a fresh disposable directory, uses synthetic data, and removes the process/data after the test. No external provider request or real email is sent.

Focused strict run: **27/27 passed, zero skips**, Node 24.21.0 with the existing test register and `INTAKE_REQUIRE_REDIS=1`. Source-only independent review closed the concurrent ready/paid projection finding. The parent owns the combined repository test/build gate.
