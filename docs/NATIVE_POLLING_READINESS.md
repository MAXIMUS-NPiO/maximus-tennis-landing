# Read-only native payment polling: prepared, not activated

This is an alternative to a PHP event publisher for **already independently bound** goods orders. `createNativeCommerceLedgerRuntime` instantiates the poller and the protected GET ledger worker calls it on the same guarded store and request deadline. The implementation is connected to the real authenticated CS-Cart/MPGS GET readers and the existing verified delivery/journal worker. It does not create a native order, payment session, charge, refund, customer, approved offer or ownership association. Current production flags/settings have not been changed.

## Required trust before the first query

The native runtime must pass its existing durable-store, current live-route, selected retrieval-version/schema and private credential gates. The registry must already contain an immutable verified association between an active verified portal customer, an approved non-TEST MX-ORD goods contract, its exact CS-Cart order/items/options/total, and its authenticated MPGS provider order. A public SKU link, customer-supplied order number, email equality or CS-Cart status `P` cannot create that association. The poller cannot import unbound store orders into a customer's account.

The supported contour is the existing maximussports.ae store, MPGS merchant `300281` at `https://ap-gateway.mastercard.com`, payment method `18`, AED, seller MAXIMUS SPORTS EQUIPMENT TRADING LLC. Actual company/storefront identifiers, the selected compatible retrieval version, live mode and native↔provider association remain independently verified configuration requirements. The official [MPGS Retrieve Order v57 schema](https://ap-gateway.mastercard.com/api/documentation/apiDocumentation/rest-json/version/57/operation/Transaction%3a%20%20Retrieve%20Order.html?locale=en_US) is a reference, not proof of the installed module's version or the actual account's configuration. The native readers and precise provisioning requirements are documented in [NATIVE_LEDGER_RUNTIME.md](./NATIVE_LEDGER_RUNTIME.md).

## Durable polling and delivery

`createNativePoller({store,scope,listBindings,discoverMovements,registerMovement,now?,signal?,production?})` exposes `pollOnce({limit:1,deadlineAt,signal,enqueueReference})`. Scope contains the inspected mapping hash, source and project. Production requires a durable store. The runtime supplies the current registry and authenticated GET readers; caller/customer JSON supplies none of these functions or identities.

Each invocation ingests at most ten current scoped registry entries through a durable CAS cursor. The registry's binding index is append-only with an atomic monotonic sequence. Only binding ID, provider-order ID, status/source/scope and immutable fingerprint enter the poller's due state. It checks at most five due bindings (the HTTP worker uses one), discovers at most twenty capture/refund transactions per binding, and attempts at most twenty opaque-reference handoffs. No customer, amount, PAN, native payment-info body or provider error text is copied into polling state or a route response.

Discovery independently rechecks the approved goods/verified-owner/native binding and retrieves the provider order. A **new** movement is independently retrieved again before the registry persists its deterministic opaque reference. Then a scoped movement unique claim and reference outbox are committed atomically. Existing durable movements skip redundant registration queries, while fresh discovery and subsequent journal verification still run their respective trust checks. Capture is processed before its dependent refunds regardless of transaction-ID sort order. A per-binding CAS movement cursor preserves progress when an invocation ends halfway through a larger movement list; useful durable progress resets consecutive-failure accounting, so a larger scan can span more than five invocations. Later refunds do not repeatedly wait behind earlier captures. Queue discovery order alone never authorizes a financial post: the journal worker still independently verifies capture/refund dependencies and can defer a refund until its capture has actually posted.

The outbox is durable before `worker.receiveReference(reference)` is called. Only the opaque string enters that worker. Its own authenticated provider/native/account checks produce verified work, and only its existing ledger stage posts a receipt or refund. Polling/discovery/reference queueing alone never posts money. Stable economic identifiers and worker idempotency prevent repeated discovery, crashes, reconstruction or a lost completion acknowledgement from duplicating a ledger entry.

Bindings are due no more frequently than once per minute; a slower deployed scheduler controls actual cadence. Transient failures back off from one second to five minutes, with at most five consecutive attempts before retained manual review. CAS leases recover after an interrupted process. Bounded due batches order by their durable due time. Missing/foreign/corrupt/stale terminal members are quarantined, stale early scores of future entries are repaired, and rediscovered nonterminal bindings/references restore lost index membership with an atomic version guard. Terminal review/completed rows are never silently revived. A reviewed case requires an independently authorized operator recovery procedure; no public poller retry/provisioning endpoint is provided.

The shared deadline stops new operations and follow-up stages; the same AbortSignal reaches the native GET readers. An atomic store operation or receiver handoff **already sent before expiry** may nevertheless finish with an acknowledgement that arrives after the caller has stopped waiting. The poller retains its lease/outbox rather than assuming either success or rollback. A later invocation rereads durable state and replays only stable idempotent operations. This is an explicit ambiguous-acknowledgement recovery contract, not a claim that all remote writes can be cancelled. Polling writes are cursor/scheduling/reference/audit metadata; the existing verified worker alone can write the financial journal.

The protected GET route exposes only five bounded counts: `bindingsChecked`, `movementsDiscovered`, `referencesQueued`, `deferred`, `reviewRequired`. They describe this invocation, not the total state of accounts or outstanding review cases. No IDs, references, proofs, credentials or native error details are returned. POST event-reference delivery does not invoke discovery. An authenticated scheduler with `COMMERCE_LEDGER_ENABLED` absent/off skips before constructing a store, credential-bearing reader or poller. MyDeposit/MyBonus programmes and bank-balance claims remain disabled.

## Current activation blockers and exact safe operator steps

The owner confirmed that hosting/server-file access is currently unavailable. PHP access is therefore unavailable for the addon-publisher option; it is not inherently required for the API polling path. CS-Cart API being enabled and an authenticated admin page do not by themselves establish a server credential or complete native/provider/account mapping.

1. Through the existing authorized administrative/provider access, inspect an authenticated read-only order response and the corresponding authenticated MPGS Retrieve Order response. Establish exact company/storefront/payment/provider-order fields, selected compatible retrieval version/schema and current live route. Do not infer capture from a configurable order status or a stored processor message.
2. Establish the approved immutable goods MX-ORD/customer/native/provider association through a trusted authenticated server/API resolver or operator provisioning process. If authorized APIs cannot prove it, existing addon/source read access remains necessary. Current empty approved offers and TEST quotations must not be renamed or copied as production evidence; the public stock-product handoff currently creates no such binding.
3. A trusted operator privately supplies the **existing** CS-Cart API user/key and MPGS API password to server-only deployment settings and records the inspected mapping/evidence. This is a concrete credential/configuration action by the owner/operator; the agent has neither read/copied these secrets nor configured them. No new merchant, account, key, privilege expansion or PSP installation is part of this implementation.
4. After those records and the proper approved goods binding exist, the operator can enable the prepared worker, confirm the deployed schedule and read/reconcile a pre-existing authorized provider movement. This readiness check need not create a new payment. A purchase with a real card remains the owner's separate action.

Until these steps are evidenced, automatic account synchronization must be reported as unactivated. The ordinary native-store product path can be released independently; that handoff alone does not constitute account/order/ledger integration.

## Local verification

Node 24 runs `tests/native-poller.test.mjs` with the repository's existing test resolver. All fixtures, bindings, evidence, amounts and credentials are synthetic. The focused suite covers invalid/foreign/unverified associations, bounded append-only cursor fairness, provider/queue outages and reconstruction, retry exhaustion/crash leases, concurrent CAS claims, repeated captures/refunds, malformed/oversized movements, isolated mapping scopes, stale/lost indexes, interrupted movement progress, deadline abort and explicitly ambiguous late acknowledgements. Its integrated worker/ledger case proves one capture plus one refund produce exactly two verified journal entries, the expected net amount and no financial-program/principal/bonus allocation or inferred bank balance. Native runtime/worker suites separately exercise the actual wired factory and isolated existing Redis. No installations, external merchant API calls, production configuration changes or real payments were performed by these tests.
