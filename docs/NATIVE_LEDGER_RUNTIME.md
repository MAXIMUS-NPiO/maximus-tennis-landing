# Native goods payment verification: source complete, runtime disabled

This stage adds real authenticated, read-only HTTPS GET clients and an immutable server binding registry. It creates no payment session, native order, merchant account, customer, evidence record or financial programme. `COMMERCE_LEDGER_ENABLED` remains absent/off by default. A flag alone cannot activate the bridge. No merchant API was called during implementation; GET responses in regression tests are explicitly synthetic.

The supported existing contour is `https://maximussports.ae`, payment method `18`, AED, MPGS at `https://ap-gateway.mastercard.com`, merchant `300281`, seller MAXIMUS SPORTS EQUIPMENT TRADING LLC. Storefront/company ID, an approved compatible retrieval API version, the current association field layout and actual provider order association remain unverified. Historical credentials, versions and order status are not substituted for these facts.

## Code contracts

`createNativeCommerceLedgerRuntime({env,store,fetchImpl?,loadCommerceOrder?,now?,signal?,timeoutMs?,maxBodyBytes?})` is async. It returns `{bridge:null,readiness:{ready:false,missing,...}}` if any gate is missing. When configured, it returns the existing durable commerce-ledger bridge, the API poller, and readiness containing `projectId`, `source`, and `mappingHash`. This digest includes the inspected versions, schemas and evidence IDs. `financialProductEnabled` is always false. Readiness describes the verifier configuration, not a real successfully reconciled order.

The platform store must be durable in production and respond to PING. The default immutable commercial loader uses the existing commerce Redis store. Operator-supplied secrets are consumed only by server code: `NATIVE_MPGS_API_PASSWORD`, `NATIVE_CSCART_API_USER`, `NATIVE_CSCART_API_KEY`. They are the existing merchant/store credentials, supplied privately by the operator; no new PSP is proposed. No configuration files are read by these modules. JSON numeric source tokens must be available in the JavaScript runtime; otherwise precision-safe processing is unavailable and the factory refuses activation. Node 24 was used for verification.

Native GETs have a six-second deadline each in this runtime, a default 256 KiB response limit, no redirect following, no cookies and no raw error preservation. The worker's shared AbortSignal reaches both readers. Enqueue performs one MPGS query and two independent CS-Cart order rechecks, at most 18 seconds of native GET deadlines, plus durable-store operations. The worker owns the overall request deadline and wraps platform store operations; a new factory is constructed for that guarded store on every request. There is no cached bridge with an unguarded store.

Four `nativeCommerceEvidence` documents must independently match mapping ID, version and complete mapping hash. Each has its exact ID, `status:verified`, non-future `verifiedAt`, an operator inspection authentication basis and one of `live_route`, `native_order_mapping`, `verified_customer_binding_schema`, `mpgs_retrieve_order_schema`. The factory does not manufacture these attestations. Evidence must be recorded through a trusted operator provisioning process after inspection of the actual configuration/source, not through a browser payload or copied synthetic fixture. No public provisioning endpoint exists.

### Native order and account association

`createNativeBindingRegistry` exposes `persistVerifiedBinding(opaqueAttestationReference)` and `persistVerifiedReference(opaqueAttestationReference)` for trusted server integration only. These require a supplied `resolveTrustedBinding`/`resolveTrustedReference` dependency that authenticates the existing addon source, server signature or independently inspected native API association. There is no fallback resolver and no public route accepting their structured records. Initial binding is never inferred from polling. The optional addon publisher is one supported ingestion path, not a requirement once a correct binding exists.

The trusted binding attestation must establish LIVE goods approval, mapping hash, native order ID, provider order ID, MX-ORD ID, company/payment/merchant/AED scope, final cash total, stable evidence ID and verified timestamp. Each native line requires an `itemBindings` record containing `nativeProductId`, positive `quantity`, `optionsHash` and the approved `commerceConfigurationHash`. Actual CS-Cart products/quantity/options digest must match this association exactly. Product IDs, grips, options or provider order fields are never guessed from a public SKU link.

Independently, the commercial MX-ORD must contain a server-approved offer with evidence, exact seller/AED/final total and consistent product/tax/shipping totals; a final technical configuration and configuration hash; verified fulfillment in an approved country; a non-TEST quotation with matching MX/order/project/seller/currency/total/terms and one exact configuration/quantity line; and server-recorded acceptance of that terms version while the offer was valid. The cash total must equal CS-Cart and MPGS. The registry stores snapshot and approval digests as immutable revisions and rechecks them before posting. Native status `P` and schema-1/plan-A alone never supply approval.

Ownership requires an active verified user, exact organization membership, existing `portalOrder` with `verified_session_and_order_capability` proof and the durable unique `portal_order_owner` constraint. A customer recorded in the immutable commercial snapshot must match. A previously guest order requires the existing capability-validated durable unique portal owner. Email is ignored. Unique claims prevent either native order or MX-ORD from being assigned to another provider association within the same inspected mapping.

Registered event references contain only the trusted provider order/transaction/kind association and evidence digests. The protected HTTP worker receives only `{eventReference}`. This reference is never parsed as a URL, customer, amount or provider identity. Fresh verification metadata does not overwrite the existing economic identity or cause a duplicate payment. Provider transaction IDs are namespaced with provider order ID because MPGS documents transaction IDs as unique within an order.

### API polling without a PHP event publisher

The registry lists only the current mapping's verified immutable bindings through a bounded append-only index in explicit ascending ordinal order. A monotonic sequence, binding document, unique association claims and index entry are committed atomically. New bindings are appended after earlier cursor positions. Listing returns only binding ID/status/source/scope/provider-order ID/fingerprint, without customer, MX-ORD, monetary amounts or evidence body. The poller owns durable due state and an opaque-reference outbox.

The real `discoverMovements` reader uses one authenticated Retrieve Order GET, selects at most 20 successful approved capture/refund transactions, and applies the same strict scalar verification as explicit-reference ingestion. It returns no raw body. Runtime discovery first rechecks the current native order, commercial approval and verified owner. `registerQueriedMovement` independently rereads the binding/native order and actual MPGS transaction, then atomically stores a deterministic `np_…` reference with `authenticationBasis:provider_server_query`. Caller amounts/customer claims are ignored; unknown binding or transaction cannot register a reference.

The protected GET worker calls `poller.pollOnce` on the same guarded store and AbortSignal, durably queues each opaque reference, and consumes the existing journal delivery queue with the remaining deadline. A scheduled deployment can therefore synchronize **already independently bound** orders through read-only CS-Cart/MPGS queries without modifying PHP or receiving an addon callback. Initial approved goods/account association still requires an independent trusted server resolver or operator provisioning; the poller cannot create that association from email/status/SKU. MPGS v57 may be selected as a supported retrieval version after real configured-query schema proof; it need not equal the PHP addon's transaction-submission version. Public documentation alone is insufficient proof.

## Verified public reference documentation

The owner task obtained the official MPGS [Retrieve Order v57 documentation](https://ap-gateway.mastercard.com/api/documentation/apiDocumentation/rest-json/version/57/operation/Transaction%3a%20%20Retrieve%20Order.html?locale=en_US) by a bounded public-doc GET. This is a reference schema, **not** the current addon/merchant API version. The locally inspected HTML SHA-256 was `7f2d6dfd1c7536a08683ec6a00de43940c62ff4bdd5f29dd6ce01481ef57f4f3`; the large source page is not included in the repository.

Documented retrieval is `GET /api/rest/version/{version}/merchant/{merchantId}/order/{orderId}` with Basic user `merchant.{merchantId}` and API password. The reader checks top-level `result`, `id`, `merchant`, `currency`, `amount`, `totalCapturedAmount`, `totalRefundedAmount`, and the unique requested transaction's `merchant`, `order.id`, `order.currency`, `order.amount`, `result`, `response.gatewayCode`, `timeOfRecord`, `transaction.id/type/amount/currency`. Only `SUCCESS` plus `APPROVED` and documented `PAYMENT`/`CAPTURE` or `REFUND` qualifies. Current support requires a single complete goods capture. Authorization, partial capture, ambiguous IDs, overcapture, overrefund, pending settlement and request-only order statuses fail closed. Monetary JSON numeric tokens retain their original decimal spelling before conversion to exact AED minor units. Supported provider identifiers are a conservative URL-safe subset of the documented 1–40 characters.

The schema contains no `liveMode` scalar that proves LIVE. The separate current configuration inspection is mandatory. If an explicit TEST/mock flag appears, it is rejected. A response's raw card/payer/sourceOfFunds/session/payment-info body is neither returned nor persisted nor used as proof. Proof contains only the digest of the allowlisted verified movement and a verification timestamp.

Official [CS-Cart Orders](https://docs.cs-cart.com/latest/developer_guide/api/entities/orders.html) and [REST API authentication/version URLs](https://docs.cs-cart.com/latest/developer_guide/api/index.html) document authenticated GET of one order, `company_id`, `payment_id`, `total`, parent order flags and products. The reader returns only core order scope, exact total, product IDs/quantity/options digests and a status explicitly labeled configuration-only. Neither `payment_info`'s provider field layout nor primary currency is guaranteed by that order contract. Independent mapping evidence must establish them; PII/payment settings are dropped.

### Deliberate remaining limitations

The documented `CHARGEBACK` transaction and `CHARGEBACK_DEBITED` dispute event do not alone prove an already settled debit; the latter says the debit will occur soon. Chargeback/reversal/funding reconciliation remains review-only until actual installed-schema and authoritative movement evidence are verified. Both explicit retrieval and discovery refuse an order history containing a successful monetary void (`VOID_PAYMENT`, `VOID_CAPTURE`, `VOID_REFUND`), chargeback, funding, refund request or unknown transaction type. These histories cannot silently contribute the old capture/refund amounts, even when each fits the remaining cumulative total. Only documented nonmonetary authentication/authorization/update/verification/void-authorization transactions can be ignored. This stage supports capture/refund only and never invents a debit from status `DISPUTED`/`CHARGEBACK_PROCESSED`. Partial/multi-capture and Multi-Vendor parent/child orders are unsupported. Payment verification is not a bank-balance assertion.

Current public SKU 9444 handoff does not produce an immutable approved MX-ORD/customer association. Existing `approvedOffers` are empty and `formalQuotation` emits TEST documents. These current requests are intentionally rejected by this adapter. Real account synchronization therefore requires a proper approved immutable goods publisher/quote contract; merely setting flags or renaming a TEST document is insufficient. Existing local TEST reconcile/webhook/invoice code remains separate and cannot supply this runtime's trusted references.

## Exact operator handoff and blocker

The owner confirmed that current server-file/hosting access is unavailable. No further permission or missing secret was requested, and no addon field names were invented. PHP access is therefore unavailable for the addon publisher option. It is **not** an unavoidable synchronization requirement: the API polling path works once verified bindings, credentials and mapping evidence exist. The remaining operator work is to inspect existing native payment configuration and authenticated API access, establish an approved retrieval version/company/provider-order/transaction mapping and independently prove native↔approved-MX-ORD↔verified-user ownership. If that association is unavailable through authorized APIs, read access to existing addon/source is needed to resolve it. A real approved goods contract and accepted terms must be supplied before a binding can be registered.

Then a trusted operator may privately provision inspected mapping/evidence and existing credentials, establish the initial immutable bindings through a trusted server/API resolver, enable the API polling worker (or optional authenticated addon reference publisher), confirm the deployed scheduler, and verify a pre-existing real provider movement through GET. That final read can establish reconciliation readiness without running a new payment. This task has not done those actions. The source cron proposal is not evidence of a deployed schedule. MyDeposit/MyBonus posting remains disabled; no rates, financial programme rules or bank balances are inferred.
