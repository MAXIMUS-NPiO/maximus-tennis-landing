# Tennis owner control payment: USD 1.00 through the embedded bank form

The owner alone makes one **USD 1.00** control payment with the bank's own payment form embedded in `https://maximus.tennis`, enters the card and completes any 3-D Secure challenge himself. The site records the attempt, hands the bank session to the documented SDK in memory, and reports "paid" only after its own authenticated read of the gateway order shows one approved USD 1.00 capture. Nothing in the browser — a callback, a return URL, a query parameter — can mark the order paid. This is a separate `payment_control` position: not goods, not a CS-Cart order, not an investment or bonus program, no delivery, and the 20 % program terms stay untouched. Any refund is a separate owner action.

This document records what is verified in code and against the gateway's published contract, what was exercised on a local production-mode stage, and the configuration the deployment still needs from the owner. It does not claim that a live payment has been made.

## 2. Server runtime

- `lib/commerce/tennis-control-authorizer.js` — the owner is the verified, active portal account whose normalised e-mail equals `TENNIS_CONTROL_OWNER_EMAIL`. One durable authorization series per attempt, byte-stable, one-use; a new series opens only when the previous one is spent (no order, expired grant, attempt past its local deadline, verified capture/refund, or review hold). No query parameter, header, form value or browser field can name the owner.
- `lib/commerce/tennis-control-order.js` — immutable `MX-CTL-…` orders in the platform store; one atomic attempt reservation with a server-generated provider order ID; repeated calls, new idempotency keys, concurrent requests and process restarts reuse the one reserved attempt. A lost acknowledgement leaves the attempt `uncertain` and never sends a second `INITIATE_CHECKOUT`.
- `lib/platform/tennis-control-mpgs.js` — the API 100 adapter: one bounded POST per operation, redirects refused, errors reduced to local codes, provider bodies never logged. `initiate` builds the payload of §1 with the return URL of the page locale; `inquire` is the Payment Options Inquiry.
- `lib/platform/native-mpgs.js` (`createTennisControlMpgsReader`) — read-only Retrieve Order projection pinned to merchant, USD and 100 minor units; `readSummary` for the owner view, `discoverMovements` for proof. A gateway timestamp up to 120 s ahead of this server is still accepted (bounded clock difference), later than that is review.
- `lib/commerce/tennis-control-proof.js` — exact USD 1.00 capture evidence (one approved `PAYMENT`/`CAPTURE`, totals consistent, complete refund history) stored once; regressions, unsupported monetary operations and disputes are a sticky `review_required`. `stored()` returns the last durable proof when the gateway is unreachable.
- `lib/commerce/tennis-control-runtime.js` — assembly from protected configuration (`readTennisControlConfig`, `buildTennisControlRuntime`); `prepare`, `initiate` (Payment Options Inquiry once per 6 h, then one session), `status`, `current`, `readinessFor`, and `system.verify` for the webhook. `deriveTennisControlPayment` maps proof + observation + attempt to the owner-facing states `not_started`, `awaiting_payment`, `authentication_pending`, `pending`, `pending_verification`, `declined`, `cancelled`, `expired`, `uncertain`, `paid`, `partially_refunded`, `refunded`, `review_required`. Only a stored capture proof yields `paid`.
- `lib/commerce/tennis-control-http.js` → `POST /api/accounts/control/{prepare|initiate|status|current|readiness}` — verified portal session cookie, CSRF, exact `https://maximus.tennis` origin, bounded JSON, allowlisted fields, re-authentication after the body and after service work, private/no-store replies through a second output allowlist. The private session descriptor is returned by `initiate` only, to the owner only, while the local attempt window is open.
- `lib/commerce/tennis-control-webhook.js` → `POST /api/control/webhook` — secret compared in constant time before the body is read; unknown or malformed orders acknowledged and ignored; one durable record per `X-Notification-ID` with appended redeliveries; a declared amount or currency outside the scope is flagged `reviewFlagged` and never applied; the acknowledgement is returned at once and the authenticated verification runs afterwards (`after()`).

## 3. Browser page `/{locale}/checkout/control`

`components/TennisControl.js` with `lib/client/tennis-control.js`, labels in `content/tennis-control.js` for all 48 locales. The page: signs the owner in through the existing account (guest → account requirement; non-owner → explicit refusal; unconfigured runtime → "not connected"), shows the server's immutable terms text verbatim, takes the owner's explicit acceptance, then `prepare` → `initiate` → loads the SDK once with the named global callbacks → `Checkout.configure` → `Checkout.showEmbeddedPage('#tennis-control-bank')`. The session ID never enters markup, URLs, storage, analytics or logs. While the attempt is open the page reads `status` every 10 s and immediately after any SDK callback; a return from the bank page is stripped from the URL before the first request and shown only as a notice. `paid`, `refunded`, `partially_refunded`, `review_required`, `expired` and `uncertain` are terminal for the page; `declined` and `cancelled` keep the bank form for a retry inside the open window. A closed attempt re-reads the account view, and the server alone decides whether a new series may open. The account page shows the owner's current control order and verified state (`TennisControlAccountStatus`); other accounts see nothing.

## 4. Security headers of the control page only

`middleware.js` + `lib/control-csp.js` set, for `/{locale}/checkout/control` and no other page:

```
Content-Security-Policy: default-src 'none'; base-uri 'none'; object-src 'none'; frame-ancestors 'self'; form-action 'self';
  script-src 'self' 'nonce-<per request>' https://ap-gateway.mastercard.com; style-src 'self' 'unsafe-inline'; img-src 'self' data:;
  font-src 'self'; connect-src 'self'; frame-src https://ap-gateway.mastercard.com; manifest-src 'self'; worker-src 'self'; upgrade-insecure-requests
Cache-Control: no-store, private · Referrer-Policy: no-referrer · X-Robots-Tag: noindex, nofollow · X-Frame-Options: SAMEORIGIN
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(self "https://ap-gateway.mastercard.com")
```

The nonce travels in the request header, so Next.js stamps its own scripts (the page is rendered per request, `dynamic = 'force-dynamic'`). The site-wide headers from `next.config.mjs` are unchanged for every other route. The API replies keep their own private/no-store/nosniff/no-referrer headers.

| `TENNIS_CONTROL_ENABLED=true` | yes | Explicit switch for the control runtime. |

| `NATIVE_MPGS_API_PASSWORD` | yes | The merchant's existing API password for API 100 (Basic auth). Never `NEXT_PUBLIC_*`. |
| `TENNIS_CONTROL_MERCHANT_ID` | optional | Defaults to the store merchant `300281`. |
| `TENNIS_CONTROL_MERCHANT_NAME` | optional | ≤ 40 printable characters; defaults to the seller's legal name. |
| `MPGS_NOTIFICATION_SECRET` | for webhooks | The 32-character secret shown in Merchant Administration → Webhook Notifications. With it, every session carries `order.notificationUrl = https://maximus.tennis/api/control/webhook`. Without it, status polling alone verifies the payment. |

## 7. Owner activation and the control payment

1. Set the variables of §6 in the Vercel project (Production) and redeploy; `POST /api/accounts/control/current` then answers `401` instead of `503 control_unconfigured`.
2. Register the owner account on `https://maximus.tennis/en/account` with the e-mail of `TENNIS_CONTROL_OWNER_EMAIL`, confirm the verification e-mail, sign in.
3. Open `https://maximus.tennis/en/checkout/control`, read the terms, tick the acceptance, start the control payment. The server first asks the gateway for the merchant's permitted currencies; a definitive answer without USD stops the attempt before any session.
4. Enter the card in the bank's embedded form and complete 3-D Secure. The page reads the result from the server; "Paid. USD 1.00 was captured and verified on the server." appears only after the authenticated Retrieve Order read.
5. Reconcile: the account page and the control page show the verified state; Merchant Administration shows the order `MC…` with one `PAYMENT` of USD 1.00; with the webhook secret configured, the delivery is recorded under the order. A refund, if wanted, is a separate owner operation in Merchant Administration; the next status read records it as `refunded`.
